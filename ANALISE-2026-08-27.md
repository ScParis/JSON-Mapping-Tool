# Análise técnica — Dev Studio (JSON-Mapping-Tool)

**Data:** 2026-08-27
**Repositório:** `JSON-Mapping-Tool-main` (monorepo "Dev Studio v3.0", autor ScParis, licença MIT)
**Escopo da análise:** arquitetura, qualidade de código, segurança e próximos passos.

---

## 1. Resumo executivo

O projeto é um **monorepo de toolkit para desenvolvedores** ("Dev Studio"), com SPA React + Vite + TypeScript no frontend e um servidor Express + TypeScript no backend, integrado ao Google Gemini. Reúne 9 ferramentas: JSON Mapper (JMESPath), CNPJ, Diff, JWT, Regex, SQL, API Client (REST), Mock Interceptor (tipo Beeceptor) e um Studio de edição/IA.

O código está **funcional e razoavelmente organizado**, com preocupação de segurança acima da média para um projeto pessoal (proteção SSRF, rate limiting, CORS por allow-list, DOMPurify no preview de markdown). O nome do repositório ("JSON-Mapping-Tool") já não reflete o escopo real (é um toolkit de 9 apps).

Os principais riscos não são de vulnerabilidade grave, mas de **prontidão para produção**: URLs de backend hardcoded (`localhost:3001`) impedem deploy real, o Mock Store é 100% em memória (perde estado a cada restart), não há CI de testes/lint, e o frontend permite guardar chaves de IA de terceiros no `localStorage` (self-XSS ou vazamento por extensões). Nenhum segredo está versionado — `.env` está corretamente no `.gitignore`.

**Veredito:** base sólida como ferramenta local/interna. Para publicar (o repo já tem `vercel.json`) faltam ajustes de configuração e endurecimento — detalhados na seção 5.

## 2. Arquitetura e stack

### Visão geral

```
JSON-Mapping-Tool-main/
├── backend/        Express 5 + TypeScript (API + proxy + mock + gemini + túnel)
│   └── src/
│       ├── server.ts      (879 linhas — todos os endpoints em um único arquivo)
│       ├── security.ts     (SSRF guard + rate limiter em memória)
│       ├── mockStore.ts    (store de mocks em memória)
│       └── *.test.ts       (2 arquivos de teste manuais)
├── frontend/       React 18 + Vite 7 + Tailwind 4 + Monaco + react-router 7
│   └── src/pages/  (1 pasta por ferramenta: JsonApp, MockApp, StudioApp, ...)
├── exemplos/       JSONs de exemplo + documentação de implementação
├── old/            Código antigo (não deveria estar versionado)
└── vercel.json     Deploy do frontend na Vercel
```

### Backend

Servidor Express 5 monolítico. Endpoints principais:

- `GET /api/cnpj/:cnpj` — proxy para ReceitaWS (contorna CORS).
- `POST /api/proxy` — proxy HTTP genérico **com validação anti-SSRF**.
- `POST /api/ai/process | /chat | /audit-hsm | /convert-image` — integração Gemini, protegidos por rate limiter (20 req/min).
- `.../api/mock/*` + `ALL /hooks/:id/*` — interceptador de webhooks estilo Beeceptor, com SSE para tempo real.
- `POST /api/tunnel/start|stop` — abre túnel público via `cloudflared` (binário) ou `localtunnel`.

Observações de arquitetura:
- Todo o backend vive em **um único `server.ts` de 879 linhas**. Funcionalmente ok, mas dificulta manutenção e testes. Candidato natural a divisão em rotas (`routes/ai.ts`, `routes/mock.ts`, `routes/proxy.ts`, `routes/tunnel.ts`).
- Estado de mock e de túnel é mantido em **variáveis de módulo / Map em memória** — não sobrevive a restart nem escala horizontalmente. Aceitável para uso local; bloqueante para produção multi-instância.
- A feature de túnel (`spawn` de `cloudflared`) expõe o servidor local à internet pública sem autenticação — ótimo para testar webhooks, mas é um vetor de risco se ligado sem cuidado.

### Frontend

SPA por rotas, uma pasta por ferramenta, com camada de UI compartilhada (`components/ui`). Pontos de destaque:
- Editor Monaco, highlight.js, marked + DOMPurify, exportação docx/pdf/xlsx.
- Camada `services/aiConfig.ts` que fala direto com OpenAI/Gemini/Claude/Grok a partir do navegador, com **fallback para o backend** (`/api/ai/process`) quando não há chave configurada.

## 3. Qualidade de código

### Pontos fortes
- TypeScript com `strict: true` no frontend; tipagem de domínio clara (`MockRule`, `InterceptedRequest`, `AiConfig`).
- Separação limpa de responsabilidades no frontend (uma pasta por app, UI reutilizável).
- Segurança tratada em módulo dedicado e testado (`security.ts` + `security.test.ts` + `test_security.ts`).
- Comentários em português explicando decisões não óbvias (ex.: por que usar objeto em vez de enum no ts-node).
- Histórico de commits com convenção (`feat:`, `fix:`, `refactor:`).

### Dívida técnica e pontos de atenção

| Item | Severidade | Evidência |
|------|-----------|-----------|
| URLs de backend **hardcoded** `http://localhost:3001` em ~20 pontos do frontend | Alta (bloqueia deploy) | `ApiApp`, `CnpjApp`, `DiffApp`, `MockApp`, `RegexApp`, `geminiService.ts`, `aiConfig.ts` |
| `server.ts` monolítico (879 linhas) | Média | `backend/src/server.ts` |
| Sem ESLint/Prettier configurado | Média | ausência de `.eslintrc*` / `.prettierrc*` |
| Uso alto de `any` (102 ocorrências em `src`) | Média | `grep ": any"` no backend e frontend |
| Testes são scripts manuais, não framework (sem Jest/Vitest) | Média | `backend test` roda `ts-node -e`; `frontend test` só faz `echo` |
| Pasta `old/` versionada | Baixa | `./old` |
| Nome do repo desalinhado do escopo ("JSON-Mapping-Tool" vs "Dev Studio", 9 apps) | Baixa | `package.json` name = `dev-studio` |
| Inconsistência de versão de TS no frontend (`devDependencies.typescript: ^4.1.2`) enquanto README anuncia TS 5.9 e usa Vite 7 | Baixa | `frontend/package.json` |
| `MockApp.tsx` com 1.407 linhas | Baixa | maior arquivo do projeto |

O ponto mais impactante é o **hardcode de `localhost:3001`**: é o que impede o deploy funcionar de verdade (o `vercel.json` publica só o frontend, que apontaria para um backend inexistente em produção). Deveria virar uma variável de ambiente (`VITE_BACKEND_URL`) centralizada.

## 4. Segurança

### O que está bem feito
- **Segredos não versionados:** `backend/.env` existe localmente mas está no `.gitignore`; só os `.env.example` são rastreados. Confirmado via `git ls-files`.
- **Proteção anti-SSRF** no proxy genérico (`validateUrlForSSRF`): bloqueia IPs privados/loopback/link-local em IPv4 e IPv6, inclusive IPv4-mapped IPv6, com resolução DNS antes da requisição. Cobertura de teste inclui ofuscações (`0x7f000001`, `0177.0.0.01`).
- **Rate limiting** (20 req/min) nos endpoints de IA.
- **CORS por allow-list** via `ALLOWED_ORIGINS`.
- **Sanitização de HTML** com DOMPurify no preview de markdown (`renderPreview`); no `JsonApp` o HTML injetado vem do highlight.js (entrada escapada), portanto seguro.

### Riscos identificados

| # | Risco | Severidade | Detalhe |
|---|-------|-----------|---------|
| S1 | Chaves de IA de terceiros guardadas em `localStorage` e enviadas direto do navegador | Média | `aiConfig.ts` salva `apiKey` (OpenAI/Gemini/Claude/Grok) em `localStorage`; expostas a qualquer XSS ou extensão do browser. Claude ainda usa `dangerously-allow-browser: true`. |
| S2 | `dangerouslySetInnerHTML` sem sanitização em `HsmStudio.renderFormattedBody` | Média | Injeta `bodyText` + valores de variáveis com apenas regex de negrito/itálico, sem escapar `<`/`>`. XSS possível (majoritariamente self-XSS, pois é entrada do próprio usuário). |
| S3 | CORS abre para **qualquer origem** quando `ALLOWED_ORIGINS` está vazio | Média | `server.ts` linha 29: `allowedOrigins.length === 0` → `callback(null, true)`. Default inseguro para produção. |
| S4 | Túnel público (`cloudflared`/`localtunnel`) expõe o backend local sem auth | Média | `POST /api/tunnel/start`; qualquer um com a URL alcança `/hooks/*` e o proxy. |
| S5 | Proxy genérico pode ser usado como open proxy para IPs públicos | Baixa/Média | SSRF cobre privados, mas o proxy encaminha para qualquer host público; combinado com S4, vira relay aberto. |
| S6 | Dependências com vulnerabilidades conhecidas | Baixa | `npm audit` no backend: 4 vulnerabilidades (3 high, 1 low), ex.: `brace-expansion` (DoS). `npm audit fix` resolve. |
| S7 | Rate limiter confia em `x-forwarded-for` sem proxy confiável | Baixa | Header falsificável permite burlar o limite por IP. |

Nenhum desses é uma falha crítica explorável remotamente **no uso local pretendido**. Todos passam a importar caso o projeto seja exposto publicamente (deploy, túnel).

## 5. Estado atual e próximos passos

### Estado
Working tree limpo, sem alterações pendentes. Últimos commits recentes (ago/2026) adicionaram o módulo GenerateData e correções de build para Vercel. O projeto está em fase de "preparar para publicar" (já tem `vercel.json` e commits de deploy), mas ainda não está production-ready por causa do hardcode de backend e do estado em memória.

### Recomendações priorizadas (RICE simplificado — maior impacto/menor esforço primeiro)

**P0 — desbloquear deploy (esforço baixo, impacto alto)**
1. Centralizar a URL do backend em `VITE_BACKEND_URL` e remover os ~20 `localhost:3001` hardcoded. *Dono: dev único. Prazo sugerido: 2026-09-03.*
2. Definir `ALLOWED_ORIGINS` obrigatório em produção e trocar o default de CORS de "libera tudo" para "nega" quando a lista estiver vazia (S3). *Prazo: 2026-09-03.*
3. Rodar `npm audit fix` no backend e no frontend (S6). *Prazo: 2026-08-29.*

**P1 — endurecimento e confiabilidade (esforço médio)**
4. Sanitizar o HTML de `HsmStudio.renderFormattedBody` com DOMPurify (S2). *Prazo: 2026-09-10.*
5. Proteger `/api/tunnel/*` e `/hooks/*` com token/segredo quando expostos publicamente (S4/S5). *Prazo: 2026-09-10.*
6. Persistir o Mock Store (SQLite/Redis/arquivo) ou documentar explicitamente que é efêmero. *Prazo: 2026-09-17.*

**P2 — qualidade sustentável (esforço médio, impacto de longo prazo)**
7. Adicionar ESLint + Prettier e um CI (GitHub Actions) que rode build + testes + audit.
8. Migrar os testes manuais para Vitest (frontend) e Jest/Vitest (backend); ligar o `test` real no `package.json`.
9. Quebrar `server.ts` em módulos de rota e reduzir o uso de `any`.
10. Alinhar a versão de `typescript` do frontend (subir de `^4.1.2` para 5.x) e remover a pasta `old/` do versionamento.
11. Renomear o repositório para refletir "Dev Studio" (ou ajustar README/badges), reduzindo confusão.
